## CONTRADICTIONS
- (sync vs independent (and persistence codec)) Clock: sync picks an HLC and rejects Lamport (a busy offline peer wins; a peer claiming ~2^53 wins forever). Independent picks Lamport and rejects HLC. Persistence's chunk codec stores 'baseLamport/dLamport'. → Adopt sync's HLC (l u48 ms, c u16, peer u64) with the (l,c,peer,value) order. Rewrite the persistence codec columns as delta-l varint, c varint, peerIdx, with the u16 value.
- (sync vs independent/persistence) Total order: independent and persistence compare (lamport, peerId). Sync produced a fast-check counterexample showing this diverges when a tag is duplicated. → Value is the final tiebreak, and values must be encoded canonically. Persistence's 'compare the peerId string' becomes 'compare the u64 peer'.
- (sync vs p2p vs persistence) Peer identity: sync uses 64 random bits per session, never persisted (no tracking, two tabs never collide). p2p uses a persistent random 64-bit replicaId per world per browser, for handshake and forwarder election. Persistence stores 'device' (local peerId) in kv and a players store keyed by peerId. → Use sync's per-session id for op tags and p2p forwarder election; it works equally well because the neighbour sets are re-gossiped. Key persistence's players store by 'local' only; do not persist a peer identity. If p2p needs rejoin continuity, add it after the MVP.
- (persistence vs sync/world/independent) Value encoding: persistence's codec uses a u8 value (bits 0-6 material, max 128 materials; bit 7 sharp). Sync, world and independent use a u16 (bits 0-7 material, bit 8 sharp, bits 9-15 reserved). → u16 everywhere, including in files. Also settle reserved bits: sync says non-zero reserved bits are invalid and close the connection; independent says preserve them for forward compatibility. Choose sync's rule and bump protocolVersion when a bit gains meaning; a mixed-version session would otherwise diverge on validation.
- (smoothing vs world vs independent) Mesher apron and locality: smoothing's k=6 design needs apron A=k+3=9 (a 50^3 worker grid) and measured that k+1 breaks normals (27/821). Independent uses K=3 and a 43^3 region. World's whole pipeline assumes a 34^3 padded region (1-voxel apron) and makes collision/picking re-extraction (extractLocal) depend on a contract of vertex support <=2 voxels. Smoothing's design violates that contract, so world's collision design and its 34^3 GEN_MESH cost model both fall. → Adopt smoothing's algorithm (it is the only measured one). Then GEN_MESH must generate a 50^3 region, about 3.8x the voxels of 34^3, so world's cost numbers must be re-measured; alternatively generate and cache neighbour chunks and cut the apron from them. Collision uses either stored CPU triangles bucketed per brick (world's fallback, +15-30 MiB) or extractLocal over a 9-voxel apron. Put 'k and apron derived in code' into the interface contract.
- (smoothing vs world) Player size vs tunnel clearance: smoothing's hE=0.2 guarantees a dug 1x2 tunnel keeps 0.6 x 1.6 clearance and says the capsule must be <=0.6 x <=1.6. World fixes the capsule at r 0.3, h 1.8 with eye height 1.62. A player therefore cannot walk through a 2-high tunnel they dug, which Minecraft players expect to work. → Decide explicitly. Options: (a) vertical hE <=0.05 (clearance >=1.9) with horizontal hE=0.2; (b) player height 1.5 (Minecraft sneak height) and eye height ~1.35; (c) collide against block AABBs for the vertical axis. Add the 'dig 1x2 and walk through' golden movement test to the gate.
- (smoothing vs world) Shapes the physics tuning relies on: world measured unrelaxed SN (lone block = 0.67-high bump with 54-degree sides; 1-block rise 45 degrees) and set step-up 0.6 and slope limit 50 degrees from that. Smoothing's final shapes differ (bump +0.75 binary, +0.45 hinted; dent -1.10). → Re-derive step-up and slope constants from the signed-off smoothing gallery shapes, not from unrelaxed SN.
- (smoothing vs rendering vs independent) Material shading: rendering puts 8 per-vertex unorm8 material weights on every vertex, interpolated. Smoothing rejects per-vertex blend weights (a single placed block dilutes to ~25%) and instead splits vertices per (corner, material), giving each quad its owning solid block's material. Independent weights by counting corner materials, which is the diluting variant. → Smoothing's model: split vertices per material. Rendering's 20 B vertex can keep the slot layout with one-hot weights, which later soft blending can use, or drop to a u8 material id. Either way, the per-cell count weighting is out.
- (smoothing vs rendering vs independent) Vertex quantisation and formats: smoothing uses 1/256 offsets as Int16 local fixed point (range -128..8448), octahedral snorm16x2 normals and u16 indices. Rendering uses uint16 at 1/1024 block, snorm8x4 normals and uint32 indices. Independent uses 1/256 with a -1 voxel bias. → The mesher quantises to 1/256 (seam proof); any renderer encoding that exactly represents 1/256 steps is fine. Pick one: uint16 at 1/1024 with a -0.5 bias covers -0.5..63.5, enough for N=32. Take uint32 indices (rendering: a sharp-cube chunk can exceed 65,535 vertices). Normal precision is a visual choice.
- (rendering vs independent) Freeing GPU ranges: rendering says freed ranges may be reused immediately via writeBuffer (spec-verified queue ordering). Independent frees only after onSubmittedWorkDone. → Rendering's rule is correct and simpler; keep the fence-free reuse and a unit test in the allocator/scheduler.
- (rendering vs world vs independent vs smoothing) Reference hardware and defaults: rendering treats i7-1255U/Iris Xe as the reference at a 160-block default and 2.1 MP cap. World treats Iris Xe as the floor (R=128) and 780M/Arc 140V as the target (R=192, 2.3 Mpx). Independent uses Arc/780M as reference with Iris Xe as floor, R=192 and DPR<=1.5. Smoothing says R 6-8 chunks. → One table in the plan: the target class (e.g. Arc 140V/780M on Windows) sets the 60 fps pass; Iris Xe is the floor preset. Fix the default R only after R0 measurement on the owner's laptop in Windows Chrome. One pixel cap (~2.1-2.3 MP).
- (rendering vs world) Triangle budget: rendering estimates ~240k triangles pre-cull at R=160 (9.4 R^2). World projects 1.22 M total at R=192 from measured test terrain with caves. That is roughly a 3-4x disagreement. → Use world's measured-terrain number for budgeting and re-measure with the real generator in R0. The GPU estimate of 6-10 ms may be optimistic.
- (persistence vs world) Thread ownership: persistence says persistence runs 'in the same worker that owns the world state'. World puts WorldStore and EditLog on the main thread with stateless workers. → World's model. IndexedDB writes run from the main thread (async, batched) or a dedicated persistence worker that receives encoded dirty-chunk blobs. State the single owner in the plan.
- (persistence vs sync vs independent) Import semantics: persistence always imports as a new world (fork; merge post-MVP). Sync says 'import is the same join' and adds an import-merge equivalence test. Independent offers both. → MVP: fork by default plus 'merge into existing world with same worldId/seed/generator', implemented as the sync join. It costs little because the stamps are kept, and sync already specifies that import refuses l > now+60 s.
- (smoothing vs sync) Removing edits: smoothing recommends that placing back a block equal to the generated state drops the edit record so the hint returns. Sync precondition P6 forbids ever deleting an entry, because deletion lets an older op win again. → Never delete. Derive 'shapeEdited' by comparing the entry's value with the generated value, which restores the hint without touching the LWW store.
- (sync vs p2p) Channels: sync wants three channels (ctl reliable, bulk reliable, pos unreliable) with bulk kept separate to avoid head-of-line blocking. p2p designs only Trystero's single reliable channel plus a negotiated 'pos' channel (id 42; independent uses id 7). → Add a second negotiated channel 'bulk' (e.g. id 43, reliable, ordered) on getPeers()[id], created on both sides in onPeerJoin, and cover it in the Chromium E2E. Fix channel ids in config.ts.
- (sync vs p2p) Handshake contents and partial-mesh relay: p2p's handshake carries {proto, build, worldId, replicaId, name}; sync's HELLO also needs seed, generatorVersion, genCanary, wallMs (skew check) and hlc. Relay: p2p uses a deterministic forwarder per missing link plus op flooding (TTL 2). Sync forwards state-changing ops to peers not directly connected to the origin. Anti-entropy period: 15 s (sync) vs 30 s (independent). → Carry sync's HELLO fields inside Trystero's onPeerHandshake. Choose one forwarding rule: sync's forward-on-change, which terminates because each replica changes at most once per op, for ops; p2p's forwarder for positions. Use 15 s.
- (p2p vs independent) Relay/tracker/STUN lists: independent names purplerelay.com (p2p measured it rejecting writes, disk full) and relay.mostr.pub, trackers including tracker.btorrent.xyz (p2p measured it unreachable), and all 4 Trystero STUN defaults. p2p pins 6 probe-verified relays and 2 STUN servers. → p2p's measured list, re-probed at release. Independent's list must not be used.
- (p2p vs independent vs build vs persistence) Room secret and link format: p2p uses one >=100-bit secret as roomId with no password, link '#j='. Independent uses an 80-bit roomId plus a 128-bit key derived from a 100-bit code, link '#v=1&c=&s=&g=&w=&r='. Build uses '#join='. Persistence reserves 'j=' and 'w=' (w = world share). → One secret (p2p). One fragment grammar in the plan: j (join secret), sig, r (relay hints), optionally s/g (seed, generator, from independent) so the joiner can start rendering before a peer answers. w= is reserved for post-MVP world-in-URL.

Sync, world, persistence and independent all rely on an ESLint no-restricted-properties rule for generator determinism. → TS ~6.0.3 plus ESLint 10 with typescript-eslint 8.70.x; add eslint to the build's check script. - Define 'same world' as identical block state (a world hash shown in the debug overlay and asserted in E2E). The mesher version is not part of world identity, so peers with different smoothing still agree.
- Treat the join link as a rendezvous, not a copy: carry seed and generator (s=, g=) so the joiner can render terrain before any peer answers. Asynchronous sharing goes through export files.
- A dev:lan script with @vitejs/plugin-basic-ssl, because a plain-http LAN IP has no navigator.gpu or crypto.subtle. That breaks both WebGPU and Trystero.
- A coarse-pointer / no-keyboard notice ('desktop keyboard and mouse required'), because Android Chrome ships WebGPU and mobile is out of scope.
- @invariant on the WGSL position output, as extra insurance for bit-identical border vertices across pipelines.
- A strict static server with no SPA fallback for E2E (vite preview uses sirv single:true, which hides broken paths). Build's serve-gateway already covers this; state the reason in the plan.
- ESLint bans complementing the dist audit: history.pushState/replaceState, navigator.serviceWorker.register, localStorage in core, and leading-slash URL strings. This catches issues at source before build.
- An accessible fallback message (focus on the heading, axe in Playwright) for the no-WebGPU path.
- A docs/acceptance.md agreed before the renderer milestone that names the reference machine, resolution, view distance, scripted scenario, metrics and network conditions.
- A BroadcastChannel loopback transport for multi-page Playwright convergence tests, cheaper than a local Nostr relay for the core-sync E2E (keep p2p's local-relay test for the Trystero adapter).
- Note that the repo .gitignore ignores '*.seed', so never use a .seed file extension.
- Unknown material ids render with a 'missing' texture rather than failing (forward compatibility for files and IndexedDB), while the sync wire keeps strict validation.
