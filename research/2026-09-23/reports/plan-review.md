## requirements-3 [major] §8.1 'Measured throughput', §1 'Measured', C-12, §15 row 'no stalls'

The figures therefore do not support the 'must not stall' requirement or C-12's '≤ 2 frames p95' definition of 'immediately'. The critique asked for these numbers to be re-measured; the plan kept them as if they had been. A back-of-envelope check shows why this matters for C-12:
- About 15% of edits dirty 8 chunks, since (17/32)³ ≈ 0.15, so the p95 falls on 8-chunk transactions.
- With 4 free workers, 8 cave chunks take 2 rounds × 10.2 ms ≈ 20 ms on P-cores.
- On E-cores it is about 40 ms, taking the world report's estimate that E-cores are up to 2× slower.
- Add up to 4 ms of main-thread assembly.
That exceeds two 60 Hz frames (33 ms). This is unverified, because the 10.2 ms is an upper bound.

## requirements-7 [minor] §11.6 Import step 3 and Import modes; §10.2 clock; §11.4 shared-gateway reads
ISSUE: Import refuses any entry with l > now + 60 s. That contradicts the plan's own rule that acceptance depends only on an op's bytes, and its claim that Merge 'is exactly the sync join'. Live sync defers such ops; import refuses them.

Scenario: a world edited while the system clock ran fast. Dual-boot RTC offsets put clocks hours off until NTP corrects them. After the correction:
- The user's own backup cannot be re-imported, so 'Export a world to a file and import it again' fails.
- The handoff fails, because it uses 'the normal importer'.
- Reloads on shared-gateway origins may reject the world, since 'every read goes through the import validator'.
- Because 'Opening a world sets l ≥ the largest stored l', every new edit is stamped in the future. Peers defer those edits into a 1,024-op queue whose overflow closes the connection. The handshake still passes, because the current clocks agree.

Separately, share-profile files keep worldId but rebase their stamps to a small counter. A Merge would apply them with stamps that lose to every existing entry.
EVIDENCE: §10.3: 'Rejecting an op based on local time would diverge permanently from a peer whose clock is fast.' P2: 'Acceptance depends only on the op's bytes.' §11.6: 'Parse strictly: … `l ≤ now + 60 s`'; 'Merge: … It is exactly the sync join'; META includes worldId in both profiles; 'stamps rebased to an order-preserving counter'. sync.md: 'Park it in a per-connection queue of at most 1,024 ops; an overflow closes the connection' and 'Imports: a world file with l > now + DELTA_FUTURE is refused … clamping would diverge' (true for Merge, not for Fork).
FIX: Fork, the default, should accept future stamps and rebase them to an order-preserving sequence ending at local now. A fork is a new world, so nothing can diverge. Merge should use live sync's deferral rule rather than refusal. Share-profile files should carry a fresh worldId or a META 'forkOnly' flag, so Merge refuses them. Storage reads on shared-gateway origins should validate structure only, with no wall-clock bound. On world open and in HELLO, if the stored max l or the peer's HLC exceeds now + 60 s, show 'this world's edits are stamped N min ahead; peers will hold them until <time>' instead of looping queue overflows and reconnects. Add a test: a backup stamped 2 h ahead imports as a Fork.

# LENS consistency
OVERALL: All the constants and cross-references I checked agree: every C-/D- and § reference resolves, the region sizes (38³ and 50³ with k = 6), the clearance arithmetic (hE = 0.15/0.05 gives (W − 0.3) × (H − 0.1)), the 16-byte vertex layout, the 21-character join code and the relay counts. The plan is not internally consistent where the critique merged research reports. REMESH drops the hints the smoothing design needs, which breaks its own seam guarantee. The §8.1 throughput figures come from a different, cheaper mesher. The chunk codec's peer index has no canonical table and none on the wire. ## consistency-1 [major] §8.1 Worker pool and jobs (REMESH, Returns), with §5.2 Hints, §6.1, §6.7 Seam guarantee
ISSUE: The REMESH input cannot produce the same mesh as GEN_MESH. The mesher needs ρ = hint/127 for every block that is not shape-edited, and it needs each edited cell's generated value to work out `shapeEdited` (§6.1, §5.3). REMESH, though, carries only a 'padded copy' of block values that the main thread assembles. GEN_MESH's return list has no hints, and the main thread keeps hints only 'for dense chunks near the surface', so uniform chunks in the 9-block apron have none. In a REMESH region every block is then 'hint-less', so the relax set R covers the whole region. After any edit the dirty chunks fall back to binary relaxation, which brings back the terracing C-7 measured (7–11° rms). Their border vertices also no longer match neighbours meshed by GEN_MESH with hints. That breaks §6.7's 'computed in both chunks from identical inputs' seam guarantee. The research's fallback for a missing neighbour was also dropped.
EVIDENCE: PLAN §5.2: 'a parallel Int8Array of generator density hints (§6.1) for dense chunks near the surface.' §8.1: 'Returns: transferred block data, render mesh and collision/pick buffers' and 'REMESH {coord, padded copy, version} … assembles the 50³ region from loaded voxels'. §6.5: R = 'vertices whose cell contains a shape-edited or hint-less block'. smoothing.md §5: 'The worker receives a copy of the 50³ neighbourhood (occupancy, flags, hints; about 125 kB per byte-plane)'. smoothing.md §1: 'if hints are absent … every block counts as hint-less'. world.md: 'If any of the 26 neighbours isn't loaded … fall back to GEN_MESH.'
FIX: Replace the REMESH line with: 'REMESH {coord, padded 50³ u16 blocks, padded 50³ int8 hints, version}. GEN_MESH also returns the core's int8 hint plane. The main thread keeps a hint plane for every loaded chunk within A = 9 blocks of a surface, uniform chunks included, or else the REMESH worker regenerates the hints itself, since that is a pure function. shapeEdited = entry.sharp || (isSolid(entry.value) !== (hint > 0)). If any of the 26 neighbours is not loaded, fall back to GEN_MESH.' Add this mesher gate test to §13: 'REMESH(state) equals GEN_MESH(state) byte for byte'.

## consistency-3 [major] §7.4 Frame cap / Automatic downgrade vs C-6 pass criteria and C-12/§8.4 edit latency
ISSUE: On a 144 Hz panel a 'steady 60' cannot be produced at all. rAF fires on vsync (6.94 ms), so 60 fps means alternating 2- and 3-vsync intervals of 13.9 and 20.8 ms, about 40% of them 20.8 ms. The p95 interval is then 20.8 ms, above the C-6 pass line of 18.3 ms. The mechanism in the research ('render only every other rAF') gives 72 fps, not 60. §7.4 still declares 'a steady 60 counts as passing'. The plan also never says what 'frame time' means. If it is the rAF interval, the '17.5 ms p95' downgrade fires continuously on such panels, and since it 'never upgrades automatically' the game ratchets down to Low. 'Edit-to-visible ≤ 2 presented frames' means 13.9 ms uncapped at 144 Hz, which the 4–11 ms per-chunk remesh budget cannot meet.
EVIDENCE: PLAN C-6: 'frame interval p95 ≤ 18.3 ms and p99 ≤ 25 ms'. §7.4: 'if p95 frame time exceeds 17.5 ms over 3 s … It never upgrades automatically' and 'on 120/144 Hz panels, a steady 60 counts as passing; there is an auto/60/uncapped setting.' rendering.md: 'If the measured GPU p95 exceeds the refresh interval, render only every other rAF for a steady 60 fps.' smoothing.md: 'about 3.6 × 4–11 ms, spread over ≥2 workers, gives 10–25 ms'.
FIX: Define the metrics independently of refresh rate. (1) Pass criterion: 'the run is done with the panel at 60 Hz; on higher-refresh panels, ≤ 1% of presented intervals may exceed 1.5× the achieved cadence (refresh ÷ n).' (2) Downgrade trigger: 'p95 of CPU+GPU work time per frame (main-thread ms + timestamp-query GPU ms) > 14 ms over 3 s', not the rAF interval. (3) Frame-cap options: 'auto / half refresh / uncapped', not '60'. (4) C-12/§8.4: 'edit-to-visible p95 ≤ 33 ms, p99 ≤ 50 ms', in milliseconds rather than frames.

## consistency-4 [major] §11.2 Chunk-entries codec, with §11.1 `peers[]`, §11.6 META, §10.2 peer id, §9.3 bulk channel
ISSUE: Codec v1 stores `peerIdx varint` and has no peer table in the blob. So: (1) 'identical states give identical bytes' is false. The index points into a per-replica table (the `worlds.peers[]` record, or META) whose order depends on the order in which each replica learned the peers, and that breaks the §13 test 'All replicas end with identical bytes and roots' and the byte-identical re-encoding test. (2) The same codec is said to be used for CHUNK_ENTRIES on the wire, but no peer table is ever sent, so a receiver cannot resolve peerIdx to the u64 that the comparator (l, c, peer, value) needs. (3) Peer ids are 'drawn fresh each session', so the persisted table grows by one u64 for every session that ever wrote a surviving entry. META is capped at 64 KiB of JSON, about 3,000 u64s as strings. A long-lived world eventually becomes unexportable, or unimportable, since the importer rejects oversized META. Persistence research used a per-device id; the critic switched to per-session ids without revisiting the table.
EVIDENCE: PLAN §11.2: 'u8 codec | varint n | varint base_l, then per entry … peerIdx varint …'; 'Canonical: identical states give identical bytes'; 'Used in all three places: IndexedDB values; the file's CHNK sections; the sync CHUNK_ENTRIES messages.' §11.6: 'META: JSON ≤ 64 KiB — … peer table'. §10.2: 'peer is 64 random bits drawn fresh each session'. persistence.md: '`peerIdx` indexes a per-replica peer table.' sync.md: 'EDITS: a peer table of at most 4 × u64'. critique.md: 'Use sync's per-session id … do not persist a peer identity.'

## render-build-1 [major] §7.3 Frame → Precision ("vec3f(origin − cameraBlock) + local − cameraFrac … bit-identical at any distance … The position output is @invariant")
ISSUE: The seam guarantee breaks on the GPU. The expression mixes an exact part (chunk delta + local offset) with an inexact camera fraction in one float chain, and WGSL lets the compiler reorder that chain. Two chunks feed different (origin, local) pairs for the same shared vertex. So `(Δ_A + 32) − F` versus `(Δ_A+32 + 0) − F` can become `Δ_A + (32 − F)` versus `(Δ_A+32) + (0 − F)`. Those round differently and can land 1 ulp apart, which shows as pinhole sparkles along chunk borders. @invariant does not prevent this: it only covers identical data in different programs. The plan's §6.6 Node tests (bit-identical quantised offsets) cannot detect a GPU-side reordering.
EVIDENCE: WGSL ED §15.7.5: "(a - b) + c reassociates to (a + c) - b … An implementation may reassociate operations." WGSL §12.10 invariant: "if the data and control flow match for two position outputs in different entry points, then the result values are guaranteed to be the same". Here the data do not match; only the geometric vertex does. The plan's own C-10 says "WGSL allows fusion and reassociation". independent.md §2 avoided this by doing the delta in integer math and only then an exact add, with no camera fraction inside the chain.
FIX: Replace the Precision bullet with: "The shader reconstructs the camera-relative position exactly in integers, `let p = (info.origin - cam.block) * 256 + vec3i(pos.xyz) - 128;` (i32, exact), then `let rel = vec3f(p) * (1.0/256.0);` (exact while |p| < 2^24, i.e. ±65,536 blocks). The camera's sub-block fraction is folded into the view matrix translation, so no float operation ever combines a per-chunk input with the fraction. # LENS net-sync-persist
OVERALL: For honest peers the core holds. Per-cell LWW ordered by an HLC with a value tiebreak converges. Forward-on-change terminates, and anti-entropy between each connected pair gives eventual delivery across a connected partial mesh. onPeerHandshake exists in Trystero 0.25.4 as the plan uses it. Against the plan's own threat model the design fails its stated guarantees: XOR digests let a member make honest peers diverge, and Trystero reassembles messages with no size limit. Several joints between areas are also broken: forwarding against anti-entropy and the rate caps, clock-ahead poisoning against deferral, share-file rebasing against merge, import modes against the handoff and room secret, the peer-table codec against the 64 KiB META cap, and Trystero's shared connections against the negotiated channels. Each has a concrete fix, and all should be settled before M1 and M7 freeze the protocol.

## net-sync-persist-1 [major] §10.3 'A peer cannot … exhaust their memory' + §9.3 Channels (Trystero actions carry HELLO/EDITS/ROOT/CHUNK_DIGESTS/WANT)
ISSUE: The '≤ 16 KiB per message, close the connection' cap and the claim that a peer cannot exhaust memory cannot hold for anything carried on Trystero actions. Trystero 0.25.4 reassembles every action in memory with no size limit before app code sees it. It also keeps completed payloads for action types the app never registered, and nothing ever frees them.
EVIDENCE: @trystero-p2p/core@0.25.4 dist/action-wire.mjs handleData: `const target = pendingTransmissions[id][type][nonce] ??= { chunks: [] }; … target.chunks.push(payload); … if (!isLast) return;` has no byte limit. For an unregistered type: `(pendingActionPayloads[type] ??= []).push({payload…})`, which nothing drains. The type (any string of 32 bytes or less) and the 16-bit nonce are chosen by the sender. `onReceiveProgress` only receives a progress byte the sender supplies, and unregistered types never reach app code, so the app cannot count bytes. Any link holder who passes HELLO can keep sending non-final 16 KiB chunks until the tab runs out of memory.
FIX: Patch Trystero with patch-package against the exact 0.25.4 pin, and re-verify the patch at the 0.25.5 bump. In handleData, drop chunks whose type is not registered, and cap pending reassembly per peer at about 64 KiB across all types and nonces; going over destroys that peer. Add a gate test that streams 10 MB of non-final chunks and asserts a disconnect with bounded heap. Until the patch lands, remove 'exhaust their memory' from §10.3's 'A peer cannot' list.

## net-sync-persist-2 [major] §10.4 Digests (chunkDigest/root = XOR of h64) vs §10.3 'A peer cannot … make honest peers diverge' and P1
ISSUE: XOR set digests are linear, so a malicious peer can build two different states with equal digests. It then leaves honest peers permanently and invisibly diverged: anti-entropy sees equal roots and never repairs them.
EVIDENCE: §10.4: 'chunkDigest = XOR of h64(cell, value, tag) … root = XOR of all chunk digests'. An XOR-sum hash is not collision resistant whatever h is (Bellare–Micciancio 1997, XHASH). Attack: M is connected to both H1 and H2. M picks about 65 cells in one chunk and two candidate entries a_i and b_i per cell. Gaussian elimination over GF(2)^64 finds a non-empty subset S with XOR_{i∈S}(h(a_i)^h(b_i)) = 0. M sends a_i to H1 and b_i to H2. Both cover the same cells, so counts match, and chunk digests and roots are equal. Forward-on-change does not forward, because both honest peers are directly connected to the origin M. The divergence is persisted, and every later joiner inherits whichever side it syncs from.
FIX: Make the chunk digest SHA-256 (crypto.subtle) over the canonical chunk-entries blob; §11.2 already promises canonical bytes. Recompute it lazily for dirty chunks before ROOT or CHUNK_DIGESTS goes out. Make the root SHA-256 over the sorted list of (chunkKey ‖ chunkDigest), sent as 16 bytes. Use no XOR at either level: an XOR of SHA-256 chunk digests is still breakable with about 257 chunks the attacker authors. Add a test that constructs an XOR collision and asserts the new digest tells the two states apart.

## net-sync-persist-3 [major] §9.3 Peer relay (forward-on-change) × §10.2 per-session peer ids × §10.3 caps
ISSUE: Forward-on-change terminates, but as written it floods on every join or merge and trips the per-connection rate cap, which closes honest connections. Eventual delivery degrades into connection churn.
EVIDENCE: §9.3: 'an op that changed local state is forwarded to peers that are not directly connected to its origin'. The origin is the entry's `peer`, which §10.2 makes 'drawn fresh each session'. So every entry from an earlier session has an origin nobody is connected to: offline edits, everything delivered by CHUNK_ENTRIES, and every merge import. Each replica that applies such an entry forwards it to all its neighbours. A join of 1e5 entries (§10.4) becomes about 1e5 EDITS per link. §10.3 caps '50 edits/s sustained, bursts of 500' per connection, and 'these close the connection'. An honest forwarder in a partial mesh that carries several players' live edits over one link can hit the same cap. P1 is already satisfied by pairwise anti-entropy on a connected graph, which is transitive.
FIX: Replace the rule with this text: 'Forward only ops received as live EDITS whose peer equals a session id announced in a current HELLO, and local edits, to neighbours not connected to that session. Entries applied from CHUNK_ENTRIES or an import are never forwarded; anti-entropy spreads them.' Rate-limit per (connection, origin session) at 50/s, so a forwarder is allowed 50/s for each live origin it carries, up to the room size minus one. EDITS whose origin is not a live session are a protocol error.

## net-sync-persist-4 [major] §10.2 Clock ('Opening a world sets l ≥ the largest stored l') × §10.3 deferral × §11.6 import
ISSUE: If the clock was ahead during offline play, the world is poisoned. The stored future stamps seed the HLC, so after the clock is corrected every stored and new edit is deferred by all peers until real time catches up (hours or days). The resulting bursts overflow the deferral queue and make the connection flap, and the player's backups and handoff are refused on import.
EVIDENCE: The local rule l' = max(l, pt) (sync.md §3) puts no bound on pt, and single-player has no skew check. §10.2 re-seeds l from the stored maximum on open. §10.3 defers any l > now + 60 s at every receiver. §11.6 import refuses entries with l > now + 60 s, and §11.5 hands off through that importer. Common triggers are dual-boot machines whose RTC is in local time (hours off until NTP corrects), manual date changes and VM restores. Once the clock is corrected, the handshake skew check passes (§9.3/D-13), yet every edit from that player exceeds now + 60 s at every peer. The offline backlog exceeds the 1,024-entry queue, 'caps … close the connection', the connection rejoins, and the cycle repeats.
FIX: Add to §10.2: 'On world open and before each local edit, if HLC l > Date.now() + 60 s, warn that the clock was N min ahead. Restamp every stored entry with l > now + 60 s to fresh local HLC stamps, keeping values and relative order, then seed the HLC from the repaired maximum.' Restamping is convergence-safe: it is an ordinary new op with the same value, and any replica holding the old, larger tag shows the same value. The importer offers the same restamp for fork and restore instead of refusing the file. Add a simulator case: offline edits at +3 h, clock corrected, reconnect, converge within one reconciliation.

## net-sync-persist-5 [minor] §10.3 Future timestamps (per-connection queue 1,024) × §10.4 'Repeat until the roots match' / ROOT every 15 s
ISSUE: Deferral plus anti-entropy has no stop rule and no deduplication. A deferred entry keeps its chunk's digest mismatched, so every round re-sends the whole chunk and queues the same entries again, until the queue overflows and the honest connection closes. A far-future op keeps its chunk mismatched for the life of the session. Memory stays bounded only because the connection is killed.
EVIDENCE: sync.md: 'Park it in a per-connection queue of at most 1,024 ops; an overflow closes the connection. Retry once a second.' Nothing deduplicates by (cell, tag). Plan §10.4: 'Repeat until the roots match' and 'ROOT every 15 s'. Roots cannot match while any entry is deferred, and an op with l up to 2^47 passes the structural check.
FIX: Keep deferred ops in one replica-wide Map keyed by (cell, tag), capped at about 4,096. On overflow, evict the entries with the largest l instead of closing the connection: they were never accepted, so 'never drop an accepted op' still holds, and anti-entropy offers them again. End a reconcile loop when a round applies nothing on either side, then schedule the next round at max(15 s, earliest deferred maturity).

## net-sync-persist-6 [major] §11.5 Handoff ('imports through the normal importer') × §11.6 Import modes × §11.1 roomSecret
ISSUE: No import path restores a world as itself. The handoff, and any export/import between origins, therefore forks a multiplayer world: it gets a new worldId and loses its room secret, so it can never sync with its group again. This undermines C-3's mitigations.
EVIDENCE: §11.6: 'Fork (default): a new worldId' and 'Merge: only when worldId, seed and generator match'. critique.md line 32 settles Merge as 'merge into existing world with same worldId', which a fresh release origin does not have. roomSecret lives only in the `worlds` store (§11.1); META lacks it (§11.6). §9.3 refuses 'a different world in the same room'.
FIX: Add a third mode: 'Restore: allowed when the file's worldId does not exist locally; keeps worldId, lineageId and stamps; equivalent to a sync join into an empty replica.' The handoff always uses Restore, or Merge if the world already exists. The handoff message carries each world's roomSecret beside the files, not inside them, so a backup shared with someone else never leaks it. Gate test: hand off, rejoin the old room, roots equal.

## net-sync-persist-7 [major] §11.6 Share profile ('stamps rebased to an order-preserving counter') vs 'Merge … is exactly the sync join' and §13 'Import-merge equals live sync'
ISSUE: Rebasing stamps in share files breaks the merge equivalence. Rebased stamps are tiny compared with real HLC milliseconds. Merging a newer share file into an older copy of the same world therefore keeps the older values, and the result matches neither party.
EVIDENCE: A share file keeps worldId in META (§11.6), so Merge is allowed. Real stamps are about 1.8e12 ms, while rebased ones are counters. Every cell the sender changed since the recipient's copy loses to the recipient's older, real-stamped entry, and the rebased tags stay in the live CRDT forever (P6). The critique introduced both merge (critique.md line 32) and rebasing (line 68) without reconciling them.
FIX: Share-profile files omit worldId, and the importer always forks them (new worldId, lineage kept), so Merge and Restore never see rebased stamps. State the merge≡sync test for profile 0 only, and add a test that a profile-1 file cannot be merged.

## net-sync-persist-8 [major] §9.3 Channels ('The two extra channels are created on both sides from getPeers()[id]'; negotiated ids 42/43)
ISSUE: Trystero 0.25.4 shares one RTCPeerConnection per (appId, remote peer) across rooms and keeps it for 123 s after leaving. Creating 42/43 again on a rejoin, or on a secret rotation (D-15), throws OperationError. If two rooms were ever joined at once, their pos/bulk traffic would share one channel with no room framing.
EVIDENCE: core@0.25.4 strategy.mjs sets `sharedPeerIdleMsDefault = 123333` and `connectPeer` reuses `sharedPeerMap[peerId]` for any room of the same appId. shared-peer.mjs: a room's `peer.destroy()` is `detachBinding` followed by `scheduleIdleTimer`, and the PC is not closed. room.mjs: `getPeers()` returns `shared.peer.connection`. WebRTC spec, createDataChannel: 'if the value of the [[DataChannelId]] slot is being used by an existing RTCDataChannel, throw an OperationError'. Trystero adds room framing only to its own channel, so CHUNK_ENTRIES on a shared bulk channel would be merged into the wrong world, which P6 makes irreversible. onPeerHandshake itself does exist in 0.25.4 (handshake.mjs). getPeers() lists only activated peers, so the channels must be created in onPeerJoin.
FIX: In trystero-transport, keep a WeakMap<RTCPeerConnection, {pos, bulk}>. Create the negotiated channels once per connection in onPeerJoin and reuse them across rooms. Prefix every pos and bulk frame with a 4-byte room epoch (a hash of worldId and secret) and drop frames that don't match. Never join two rooms at once, and close the channels only when the connection closes. Gate test: leave and rejoin the same room within 5 s, with no OperationError and sync continuing.

## net-sync-persist-9 [major] D-5 ('You evict someone by rotating the link') × D-15 (secret kept per world) × §17 (rekey/kick and topic rotation deferred)
ISSUE: With every member storing the secret and no rekey in the MVP, rotating the link does not evict anyone. D-15 also turns the relay topic into a permanent identifier for the group, and the plan does not say so.
EVIDENCE: §11.1 stores roomSecret per world on each member; §17 defers 'host rekey/kick' and 'rotating the relay topic daily'; §10.3 'Eviction means a new link'; P6 never deletes. After A rotates, any member who reopens the world uses the stored old secret and meets the evicted player E again. That member merges E's edits and carries them into the new room at the next contact, and E keeps the old secret forever. Relays see SHA-1('Trystero@amorfus@secret') (§9.5), so a fixed secret lets them link the group's IP addresses across every session.
FIX: Reword D-5: 'Rotation stops future meetings only after every remaining member switches; edits already merged stay.' Add a minimal MVP rekey: 'New invite link' sends REKEY{newSecret} directly, never forwarded, to the peers the user ticks. Each receiver replaces its stored secret, marks the old one superseded and refuses to reuse it, and leaves the old room. D-15 should name the linkability cost. §9.5: a stored secret is used only after an explicit Host or Join, never automatically when a world opens.

## net-sync-persist-10 [major] §11.2 Chunk-entries codec (peerIdx) × §11.1 worlds.peers[] × §11.6 META 'JSON ≤ 64 KiB … peer table'
ISSUE: peerIdx points into a peer table that lives outside the blob, differs between replicas and keeps growing, and that table sits in size-capped JSON. As a result the codec is not canonical, cannot be sent on the wire as-is, and a world can be made impossible to export or import.
EVIDENCE: The table's order depends on arrival history, so 'identical states give identical bytes' fails, and a peerIdx in CHUNK_ENTRIES means nothing to the receiver. Peer ids are fresh each session (§10.2) and unauthenticated (§10.3 checks only peer ≠ 0). A u64 must be a JSON string of about 22 bytes, so about 2,900 ids exceed the 64 KiB META cap. A member can create that many fake peer ids in about 60 s at the allowed 50 edits/s; after that, every replica's export and handoff produce files the importer rejects, and long-lived honest worlds eventually hit the same limit. A heavily edited chunk (32,768 entries × about 9 B ≈ 290 KB) also exceeds §9.3's 'Every message is ≤ 16 KiB', and no fragmentation rule is given. Δl itself is fine: entries are sorted by ascending l, so it is never negative.
FIX: Redefine codec v1 as `u8 codec | varint npeer | u64le × npeer (strictly ascending) | varint n | varint base_l | entries`, with peerIdx indexing the blob's own table. Peer order then equals peerIdx order, and the canonical-order check is local to the blob. Remove peers[] from the world record and from META. On the wire, split a chunk into parts that are each valid v1 blobs over contiguous runs of the canonical order, cut greedily at 16 KiB or less. Parts apply independently, so no reassembly buffer is needed.

## net-sync-persist-11 [minor] §9.3 Handshake ('A joiner with no local copy … adopts the header from HELLO')
ISSUE: The join handshake does not cover a joiner that has no world yet, a joiner that already holds the world under an older secret, or two worlds sharing one secret.
EVIDENCE: The link carries only the secret (§9.2). HELLO requires worldId, seed, generatorVersion and genCanary, and refuses 'a different world in the same room', but the plan never says what a joiner sends before it has a world, or what happens when two such joiners meet first. `worlds` is keyed by worldId (§11.1). If a joiner already holds that worldId (after a rotation or a restore), 'creates the world' collides with or overwrites its local copy and offline edits, and the plan does not say whether the stored secret is updated. If 'Save as copy' (D-6) copies roomSecret, two worlds end up in one room.
FIX: Add `hasWorld` to HELLO. A peer without a world skips the world checks and sends only HELLO and ROOT(count 0). The joiner binds to the first HELLO that carries a world. If that worldId exists locally, the joiner opens it (taking the Web Lock, or showing 'open in another tab') and replaces its roomSecret with the link's; otherwise it creates the world. Every later HELLO must match. Fork, Save-as-copy and share imports never copy roomSecret.

## net-sync-persist-12 [minor] §9.3 Refusals ('room full (8 players)')
ISSUE: The room cap is decided separately by each peer and can race. Forwarding carries a refused peer's data anyway, and nothing makes the refused joiner leave the room.
EVIDENCE: Each peer applies the cap in its own onPeerHandshake using its own count. Two joiners arriving together in a 7-player room can each be accepted by different peers, leaving 9 players in a partial mesh; forward-on-change and the position forwarder then relay the 'refused' player. After a handshake failure Trystero only detaches the binding and keeps the shared connection for 123 s. It keeps announcing the refused joiner as long as that joiner stays in the room, so the handshake repeats.
FIX: On any room-full refusal, the joiner calls room.leave() and shows the message. Make admission deterministic: members gossip their member sets. When more than 8 are known, every peer refuses the latest arrivals by (first-seen HELLO time, session id), and no peer forwards for a refused session.

## net-sync-persist-13 [minor] §11.5 Handoff security
ISSUE: Only the receiving side is protected. The old build posts the whole backup (stamps and player state) to whatever origin the URL fragment names. An old build cannot recognise a future release's CID.
EVIDENCE: §11.5: '#amorfus-handoff=<nonce>&to=<origin> … The receiver checks event.origin and the nonce.' Any page can open the old release with `to=*` or with its own CID origin. `to` comes straight from the fragment, and '*' as targetOrigin delivers the message to any opener. The e2e covers only 'two localhost origins'. ## feasibility-8 [minor] §11.1 'Reads' vs §8.1 GEN_MESH and §10.4 ROOT; M4/M6/M7 coupling
